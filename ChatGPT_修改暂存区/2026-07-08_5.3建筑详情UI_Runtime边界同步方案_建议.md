## 三、方案目标

本方案用于准备 `5.3 建筑详情 UI.md` 的单文件正式回写，明确后续正式回写时只补充 Runtime 只读边界。

后续正式回写不得新增 UI 实现，不得新增诊断算法，不得修改 Runtime，不得修改 C# / Unity / 测试代码。

## 四、后续正式回写只应补充的内容

### 1. 建筑详情 UI 只能读取 Runtime 输出

后续正式回写只建议补充以下边界：

- 建筑详情 UI 读取 Runtime State / Event / Diagnostics。
- 建筑状态、施工状态、运行/暂停状态、工位状态、输入、输出、库存、等待原因、可用/不可用原因，应来自 Runtime。
- UI 不能自行裁决建筑是否运行、是否缺资源、是否缺工人、是否缺燃料、是否缺光照、是否结构失效。

### 2. 建筑详情 UI 不得复制 Runtime 算法

后续正式回写应明确 UI 不得自行计算：

- 生产
- 库存
- 物流
- 承重
- 光照
- 燃料
- 消耗
- 等待原因
- 可用/不可用原因
- 诊断优先级

### 3. Diagnostics 读取边界

后续正式回写只建议补充以下 Diagnostics 读取边界：

- UI 可以展示 `StateDiagnostics` / `DiagnosticIssue` 的结构化字段。
- UI 可以展示 TargetIds / Priority / SourceSystem / Message 等 Runtime 已输出字段。
- UI 不得解析自然语言 `Message` 作为规则来源。
- UI 不得维护第二套诊断优先级。
- UI 不得复制光照、物流、生产、燃料、承重、库存算法来生成诊断。

### 4. Command 边界

后续正式回写只建议补充以下 Command 边界：

- 建筑详情 UI 如需触发玩家操作，只能提交 Command。
- UI 不得直接修改建筑 State。
- UI 不得直接修改资源库存。
- UI 不得直接修改岗位分配。
- UI 不得直接修改生产进度。
- UI 不得直接修改暂停/运行权威状态。

## 五、后续正式回写不得修改的内容

## 七、建议正式回写方式

后续正式回写时建议遵守以下方式：

1. 只修改 `文明块/05-UI 与交互设计/5.3 建筑详情 UI.md` 一个正式文件。

5. 提交后核对实际修改文件，确认未修改 Runtime / C# / Unity / 测试代码。
