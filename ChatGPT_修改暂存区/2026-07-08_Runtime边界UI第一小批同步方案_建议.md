# Runtime 边界 UI 第一小批同步方案建议

本文件位于 `ChatGPT_修改暂存区/`，仅作为 Runtime 统一权威边界后续同步到 UI 文档的第一小批方案建议。

本文件不修改正式规则源，不替代 `5.1 全局界面.md`、`5.2 建造系统 UI.md`、`5.3 建筑详情 UI.md`，不创建 PR，不代表 UI 实现任务，不代表新增 Runtime 功能，不代表修改代码。

  - `5.1 全局界面.md`
  - `5.2 建造系统 UI.md`
  - `5.3 建筑详情 UI.md`

## 三、方案目标

本方案用于准备 UI 三文件的小范围同步方案，明确每个文件后续正式回写时只应该补充哪些 Runtime 读取 / Command 边界。

本方案只做范围界定，不直接修改正式文件，不新增 UI 需求，不扩展 Runtime 系统，不改变建筑数值。

## 四、逐文件同步范围建议

### 1. `文明块/05-UI 与交互设计/5.1 全局界面.md`

后续正式回写只应补充：

- UI / View 只能读取 Runtime 输出。
- UI / View 只能提交 Command。
- 全局界面的资源、人口、工人、时间、诊断、提示等展示应以 Runtime State / Event / Diagnostics 为准。
- UI 不得修改权威 State。
- UI 不得复制 Runtime 生产、库存、物流、承重、光照、燃料、消耗算法。
- UI 不得维护第二套诊断优先级。

不得写成：

- 新 UI 实现任务。
- 新仪表盘需求。
- 新教程、任务、商店、科技、挑战系统。
- 新 Runtime 系统。

### 2. `文明块/05-UI 与交互设计/5.2 建造系统 UI.md`

后续正式回写只应补充：

- 建造 UI 只能构造建造 / 取消 / 拆除 / 放置相关 Command。
- 建造 UI 只表达玩家意图、提交请求、展示 Runtime 返回结果。
- 建造可用性、资源扣除、占地、承重、施工状态必须由 Command / Simulation 裁决。
- UI 不得直接扣资源。
- UI 不得直接创建建筑。
- UI 不得直接推进施工。
- UI 不得绕过 CommandBus / Simulation。

不得写成：

- 新建筑卡需求。
- 新建筑数值。
- 新放置规则。
- 新施工队列系统。
- 修改水井成本。
- 修改 `6.1`。

### 3. `文明块/05-UI 与交互设计/5.3 建筑详情 UI.md`

后续正式回写只应补充：

- 建筑详情 UI 只能读取 Runtime State / Event / Diagnostics。
- 建筑状态、生产、库存、物流、承重、光照、燃料、消耗、等待原因、可用/不可用原因必须来自 Runtime。
- UI 可以展示结构化诊断字段。
- UI 不得解析自然语言 Message 作为规则来源。
- UI 不得自行计算生产、库存、物流、承重、光照、燃料、消耗。
- UI 不得维护第二套建筑运行规则或第二套诊断优先级。

不得写成：

- 新建筑详情 UI 实现任务。
- 新内部视图。
- 新全屏切入。
- 新建筑模拟。
- 新生产算法。
- 新诊断算法。

## 五、分批顺序建议

建议后续正式回写顺序：

1. 先 `5.3 建筑详情 UI.md`，因为它最直接涉及 Runtime 诊断与状态读取边界。
2. 再 `5.1 全局界面.md`，同步全局 UI 只读边界。
3. 最后 `5.2 建造系统 UI.md`，同步 Command 提交边界。

如果用户更重视建造入口，则 `5.2 建造系统 UI.md` 可以提前，但每次只改一个文件，不应一次性修改多个 UI 文件。

## 六、当前停止线

当前阶段不得进入：

- UI 实现
- 完整昼夜系统
- 联机服务器产品化
- 模组热加载
- 新 Runtime 系统
- 新存档结构
- 新 StateHash 算法
- 新协议版本
- 正式任务 / 商店 / 地下 / 科技 / 防御系统
- 新建筑数值
- 改水井成本
- 改 `6.1`

## 七、收口建议

UI 第一小批同步只应补充 Runtime 读取边界与 Command 提交边界，不应把任何 UI 需求、玩法系统、数值变更或代码实现写入当前阶段。

后续正式回写时，建议每次只修改一个 UI 文档，并在提交后核对实际修改文件，确保未修改 Runtime / C# / Unity / 测试代码。
