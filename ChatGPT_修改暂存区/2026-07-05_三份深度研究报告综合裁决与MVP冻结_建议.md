## 本轮目标

待 Codex / 用户审核后回写。

本轮目标是在已经上传并阅读三份深度研究报告后，对《文明块》下一阶段做一次总裁决：冻结 MVP 范围、冻结 Runtime 最小架构、冻结地形与建筑数据模型方向，并明确哪些系统现在必须砍掉、哪些只预留边界、哪些可以进入 MVP 后第一轮扩展。

本轮不继续新增中后期系统主题，不继续扩大系统面，不直接修改 `文明块/` 正式目录，不直接让 Codex 编写 Unity / C# Runtime。

本轮裁决的核心判断是：

> 《文明块》现在最需要的不是继续设计更多系统，而是把“第一座真的会活起来的小型体素城市”做成 MVP 的唯一中心目标。

三份报告形成的共同结论如下：

1. 《文明块》MVP 不是缩小版完整游戏，而是一个可持续运转的小型体素城市样机。
2. MVP 必须优先完成基础城市闭环，而不是把联机、模组、地下、商店、工具、正式任务、复杂 NPC 都做一个壳。
3. Runtime 必须采用轻量、清晰、单向数据流：Definition / Input / Command / Simulation / Event / ViewState / Presentation / Rendering / SaveLoad。
4. Simulation Layer 必须是唯一权威状态来源，UI、动画、Shader、粒子、摄像机、音效不得直接改游戏状态。
5. 地形与建筑模型不应采用全世界真实 3D 体素可挖可建，而应采用逻辑高度格、显式地基 / 支撑、独立地下层、逻辑通行格的混合模型。
6. MVP 阶段必须优先建立稳定 ID、存档版本、Definition / State / View 分离、Command 入口和可测试边界。
7. 当前最危险的问题是范围膨胀，而不是设计不够。

### 五、MVP 只预留边界但不实现的系统

建议正式回写时明确：

```md
### MVP 只预留边界但不实现

以下系统在 MVP 中只保留数据边界、接口边界或文档边界，不实现完整玩法：

1. 联机：只保留 Command、Event、稳定 ID、权威状态、可序列化数据边界，不实现网络层。

5. 工具制造：只在建筑定义或生产参数中预留效率挂点，不实现工具链。
6. 商店：只预留交易命令、货币字段、统一资源增减接口，不实现正式交易循环。
7. 任务：只保留轻量下一步提示，不实现正式任务链和奖励池。
8. NPC 扩展：只保留稳定 NPC ID、工位状态、居住状态，职业 / 情绪 / 社交 / 记忆延后。
9. 建筑内部：只保留内部管理抽象边界，MVP 第一批不做完整内部视角。
```

### 六、Runtime 架构冻结

建议正式回写时冻结 Runtime 最小架构为：

```md
### MVP Runtime 架构冻结

MVP Runtime 采用轻量单向数据流：

Config / Definition → Input → Command → Simulation → Domain Event → ViewState → Presentation → Rendering → Save / Load

其中：

- Definition 使用 ScriptableObject 或等价静态定义资产。
- 运行时权威状态使用纯 C# WorldState / State DTO。
- 所有状态修改必须经由 Command 进入 Simulation。
- Simulation Layer 是唯一权威状态修改层。
- Simulation 产出 Domain Event。
- ViewState 负责把权威状态整理成 UI / 表现层可读模型。
- MonoBehaviour 只负责 Presentation / Rendering。
- Save / Load 只操作 DTO，不直接依赖 Unity 场景层级。
```

### 七、Runtime 必须现在实现的六个边界

```md
### MVP 必须实现的 Runtime 边界

MVP 必须从一开始实现以下六个架构边界：

1. 权威 Simulation 独立存在。
2. Command 统一状态入口。
3. 集中 GameClock / 时间推进。
4. 集中 SimulationRandom / RNG 管理。
5. Definition 与 Instance / State 分离。
6. 可存档 DTO 与 SaveVersion。
```

### 八、Runtime 禁止越权规则

```md
### Runtime 禁止越权规则

- UI 不得直接修改资源、建筑、NPC、任务、时间、生产或战斗状态。
- 动画不得直接决定建筑完工。
- Shader 不得决定建筑是否可用。
- 粒子不得触发生产结果。
- 摄像机不得影响权威模拟。
- 音效不得推动任务完成。
- MonoBehaviour 不得成为权威状态唯一来源。
- Unity 场景层级不得决定存档结构。
- 建筑状态不得只存在 GameObject 上。
- 资源变化不得散落在 UI 脚本、特效脚本或按钮回调中。
```

### 九、地形与建筑数据模型冻结

建议正式回写时冻结如下方向：

```md
### MVP 地形与建筑数据模型冻结

MVP 不采用全世界真实 3D 体素可挖可建的统一模型。

MVP 采用混合权威模型：

- 地表：SurfaceTile / TerrainChunk 逻辑高度格。
- 建筑：BuildingDefinition / BuildingInstance 分离。
- 地基：Foundation / FoundationPlan。
- 支撑：SupportRule / SupportPlan。
- 通行：NavCell / NavLink 逻辑通行格。
- 地下：UndergroundLayer 预留分层数据结构。
- 表现：Unity GameObject / Mesh / 草 / 碎石 / Shader / 粒子只读权威状态。
```

```md
### 地形建筑默认常量（MVP 暂定）

- 地表逻辑格：1.0m × 1.0m。

- Surface Chunk：32 × 32。

- 需地基阈值：0.5m < 高差 ≤ 2.0m。
- 支柱最大垂落：6.0m。
```

### 十一、建筑放置合法性冻结

建议正式回写时明确建筑放置合法性检查顺序：

```md
### 建筑放置合法性检查顺序

建筑放置合法性必须依据逻辑世界，而不是视觉对象。

推荐检查顺序：

1. 地块是否在地图边界内。
2. 地皮是否属于玩家或允许建造。
3. 地皮是否已探索 / 已接入。
4. 建筑是否位于允许建造层。
5. Footprint 是否与已有建筑、施工区、禁建区或硬阻挡冲突。
6. 地形类型是否允许建造。
7. 高差是否在自动找平、地基、平台、支柱或禁止放置阈值内。
8. 地基计划是否可生成。
9. 支撑 / 承重规则是否满足。
10. 至少一个入口是否可达。
11. 是否阻断关键通路。
12. 是否与地下入口、矿脉核心或地下空腔冲突。
13. 资源是否足够。
14. 建筑定义是否存在特殊限制。
```

## 理由

待 Codex / 用户审核后回写。

提出本综合裁决的理由如下：

1. 三份深度研究报告的方向高度一致，均认为《文明块》当前最大风险是范围膨胀，而不是设计不足。
2. 现有暂存区已经有前30秒、建筑放置、表现层、工具、基础城市闭环、NPC、任务、地下、资源链、商店、UI 等多个主题，继续新增中后期系统主题会再次扩大系统面。
3. MVP 必须从“做哪些系统”转向“冻结哪些系统不做”。
4. Runtime 架构必须在写代码前固定，否则 AI 辅助开发容易让 UI、动画、MonoBehaviour、场景对象直接修改权威状态。
5. 地形与建筑模型必须在正式实现前固定，否则建筑放置、NPC 通行、地基、地下、存档和联机预留会互相冲突。
6. 地下、商店、工具、正式任务、复杂 NPC 都是高返工系统，不能在 MVP 阶段进入主循环。
7. Simulation / Command / Event / ViewState / Presentation 分离是后续存档、测试、联机预留、模组预留的共同基础。
8. SurfaceTile / BuildingDefinition / BuildingInstance / Foundation / NavCell / UndergroundLayer 是后续建筑、地形、地下、通行、存档共用的关键边界。
9. 本建议作为暂存区综合裁决，能防止三份深度研究报告被分散吸收、重复回写或被 Codex 误解为直接实现任务。
10. 当前最应该做的是“总裁决”，而不是继续写更多系统细节。
