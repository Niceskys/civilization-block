## 本轮目标

待 Codex / 用户审核后回写。

本轮目标是建立一套更稳妥的“暂存区建议 → Codex / 用户审核 → 正式文档回写 → PR 复核 → 合并”的工作流建议，避免后续继续出现以下问题：

1. ChatGPT 或 Codex 直接修改正式 A 级文档，用户难以判断是否正确。
2. 一次性大改多个正式文件，导致规则之间互相覆盖、遗漏或误伤。
3. 误把建议内容写成“已生效”“已回写”“正式定稿”。
4. 在未确认用户意图时修改 `00.3`、`00.4`、PR 描述、索引或正式目录。
5. Codex 根据单个建议文件直接实现代码，绕过文档审核和正式回写。
6. 用户被迫频繁回复“继续”，但每次只得到很少内容。

本建议希望把以后每轮工作的节奏固定为：

> 每轮一个完整主题包，先写入 `ChatGPT_修改暂存区/`，再由 Codex / 用户审核，确认后才允许小步回写正式文件。

### 一、暂存区定位建议

建议未来明确：

```md
### ChatGPT_修改暂存区定位

- `ChatGPT_修改暂存区/` 是建议暂存区，不是正式规则目录。
- 暂存区中的文件不得直接视为已生效规则。
- 暂存区中的内容必须经过 Codex / 用户审核后，才能选择性回写到正式文档。
- 暂存区文件可以比正式规则写得更完整、更发散，用于讨论和审查。
- 正式目录文件必须保持更收束、更稳定、更可执行。
- 暂存区建议与正式规则冲突时，以正式规则为准。
- 若暂存建议被采纳，必须在正式文件中重新组织语言，不得无脑整篇复制。
```

### 二、每轮主题粒度建议

建议以后每轮不再只写很小的碎片，而采用“完整主题包”：

```md
### 每轮主题粒度

- 每轮只写一个主题文件。
- 每个主题文件必须覆盖一个完整问题包，而不是只写一个小点。
- 一个主题包应包括：目标、影响文件、建议内容、理由、不确定点、禁止直接生效事项。
- 一个主题包可以涉及多个正式文件，但不得直接修改这些正式文件。
- 一个主题包应尽量让 Codex 能据此拆分出 3~8 个小回写任务。
- 主题包过大时，应拆成多个后续主题包；主题包过小时，应合并到更完整的问题包中。
```

建议主题包大小参考：

```md
适合单独成包：
- 基础城市闭环
- 建筑放置合法性与地形地基
- 前30秒留存边界
- 工具制造与前期启动体验
- 表现层与渲染层边界
- NPC施工、入住与工作反馈闭环
- 任务系统早期里程碑与非强制边界
- 地下探索与地上基础闭环边界
- Codex审核回写流程与安全边界

不适合单独成包：
- 只改一句提示文案
- 只补一个按钮名称
- 只改一个词
- 只列一个未确认问题
```

### 五、Codex 审核流程建议

建议 Codex 审核暂存建议时按以下顺序执行：

```md
### Codex 审核流程

1. 读取本轮暂存建议文件完整内容。
2. 列出建议影响的正式文件。
3. 对每个正式文件判断：需要回写 / 暂不回写 / 需要用户裁决。
4. 检查建议内容是否与现有正式规则冲突。
5. 检查是否涉及 Runtime、存档、StateHash、联机协议或测试。
6. 把建议拆成小任务，每个任务只允许修改一个正式文件。
7. 对每个小任务给出预期插入位置、替换范围和不修改范围。
8. 如果目标文件过大，只做小节插入或局部替换，不整篇重写。
9. 如果发现冲突，不直接覆盖，先写冲突说明。
10. 回写完成后列出：修改文件、修改小节、采纳内容、未采纳内容、不确定点、后续任务。
```

### 六、正式回写顺序建议

建议正式回写采用“小批次、小文件、小 PR”原则：

```md
### 正式回写顺序

- 一个回写 PR 最好只处理一个主题包。
- 一个提交最好只改一个正式文件。
- 大文件只做局部插入，不整篇替换。
- 先回写最不易误伤的说明型边界，再回写会影响数值、流程或实现的数据型规则。
- `00.3` 和 `00.4` 最后再更新，且必须由用户明确要求。
- 如果暂存建议仍在审查中，不得提前改索引。
```

优先级建议：

```md
1. 先回写建筑放置合法性与地形地基边界。
2. 再回写前30秒留存边界。
3. 再回写工具制造与前期启动体验边界。
4. 再回写表现层与渲染层边界。
5. 再回写任务系统早期里程碑与非强制边界。
6. 再回写 NPC 施工、入住、待分配、空闲反馈边界。
7. 最后再处理 `00.3`、`00.4`、索引和路线图同步。
```

### 七、PR 创建与合并建议

建议后续 PR 流程如下：

```md
### PR 流程

- 暂存区建议可以先累积在同一工作分支。
- 当暂存区形成一个完整审核包后，再创建 PR。
- PR 标题必须写明是“暂存建议”，不能写成“正式规则回写”。
- PR 描述必须列明：只改暂存区、不改正式目录、不改 Runtime、不改索引。
- 若 PR 只包含暂存区建议，可以不更新 `00.4`。
- 合并前检查 changed files，确认没有 `文明块/` 正式目录文件。
- 合并前检查是否误改旧 PR 描述、正式索引或 Runtime 文件。
- 合并前由 ChatGPT 给出主审判断，但不替用户隐藏风险。
```

建议 PR 描述模板：


## 理由

待 Codex / 用户审核后回写。

提出本建议的理由如下：

1. 用户已经明确不希望频繁回复“继续”才能推进很少内容，因此需要把每轮产出改为完整主题包。
2. 用户也明确要求不要直接修改《文明块》正式文档目录下的文件，因此暂存区需要明确地位和流程。
3. 之前曾出现误触旧 PR 描述、直接回写正式文件、尝试新增正式目录文件等问题，必须用流程减少误操作。
4. Codex、DeepSeek、MiMo 都可能在长任务中遗漏约束，因此每个建议文件和每个执行指令都必须重复关键禁止事项。
5. 暂存区允许充分展开想法，正式回写则必须收束；两者如果不分离，很容易污染正式规则体系。
6. 小步回写可以降低大文件被整篇替换、旧规则被误删、索引提前失真的风险。
7. 明确 PR 模板和检查清单，可以让用户即使专业水平不足，也能通过“看改动范围”判断是否安全。
8. 把 DeepSeek / MiMo 限制为审核或小范围执行，可以充分利用模型额度，同时避免它们擅自扩大范围。
