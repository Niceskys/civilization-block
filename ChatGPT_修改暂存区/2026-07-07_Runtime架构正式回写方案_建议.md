## 二、统一架构边界

### 1. Definition

Definition 是静态定义层，用于描述资源、建筑、配方、岗位、命令类型、事件类型和规则参数。

Definition 可以来自 ScriptableObject、配置表、JSON、Markdown 映射或等价静态资产，但进入 Runtime 后必须被视为只读输入。

Definition 不保存当前存档进度，不记录玩家当前资源，不记录建筑实例状态，不记录 UI 展开状态。

禁止行为：

- 不得在 UI / View 层临时创建第二套 Definition。
- 不得让 Presentation 直接改 Definition 来影响当前玩法结果。
- 不得把 Definition 当成当前存档 State 使用。

### 2. State

State 是权威运行状态，记录影响玩法结果的当前事实。

State 至少包括：

- 资源库存或等价资源状态；
- 建筑实例；
- 施工任务；
- NPC / 劳动力状态；
- 时间状态；
- 生产状态；
- 已处理命令或事件所需的幂等字段；
- Save / Load 所需的权威字段；
- StateHash 覆盖所需的权威字段。

State 只能由 Simulation 通过 Command 或系统 Tick 变更。

UI / View / Presentation / Animation / Shader / Camera / Audio 不得直接修改权威 State。

### 3. View

View 是只读表现层输入，用于把 Runtime 结果展示给玩家。

View 可以读取：

- State 的只读快照；
- Simulation 输出的 ViewState；
- Event 派生的表现状态；
- Runtime Diagnostics；
- 当前可见的 UI 选择状态。

View 不得成为权威状态来源。

UI / View 可以提交 Command，但不能直接写 State、不能直接扣资源、不能直接创建建筑实例、不能直接分配 NPC、不能直接推进生产。

### 4. Command

Command 是所有玩家操作和外部操作进入 Runtime 的唯一入口。

玩家建造、取消、拆除、移动、分配 NPC、切换生产、时间控制、保存、读取、调试命令和未来联机输入，都必须通过 Command 或等价命令对象进入 Simulation。

Command 必须具备：

- 明确的命令类型；
- 发起者；
- 目标对象；
- 参数；
- 校验结果；
- 成功或失败反馈；
- 必要时的幂等标识。

禁止行为：

- 不得让 UI 绕过 Command 直接修改 State。
- 不得让 Event 反向充当 Command。
- 不得为某个系统另建第二套命令入口。

### 5. Event

Event 是 Runtime 已发生事实的输出，不是修改入口。

Event 用于记录：

- 建筑开始施工；
- 建筑施工完成；
- 资源变化；
- NPC 分配变化；
- 生产完成；
- 状态诊断变化；
- 保存或读取完成；
- 其他已经发生的事实。

Event 可以被 UI、音效、动画、日志、诊断、成就、教程、遥测或网络同步读取，但不得直接成为修改 State 的入口。

如果 Event 触发后续玩法变化，必须转化为 Command 或由 Simulation 内部明确规则处理，不得由 View 层处理。

### 6. Simulation

Simulation 是权威规则执行层。

Simulation 负责：

- 校验 Command；
- 变更 State；
- 执行 Tick；
- 执行资源、建筑、NPC、生产、时间、施工、诊断等规则；
- 生成 Event；
- 生成 ViewState 或只读快照；
- 维护 Save / Load 的权威状态；
- 维护 StateHash 输入边界。

Simulation / RuntimeComposition 是单机与服务器共用的权威入口。

单机模式下，RuntimeComposition 在本地进程中执行 Simulation。

联机模式下，Server 才是权威 Simulation 执行者，Remote Client 不推进权威 Simulation。

### 7. Save

Save 只保存权威 State，不保存纯 UI 状态。

Save 必须保存影响玩法结果的状态，例如资源、建筑、施工、NPC、生产、时间、解锁、持久化命令或幂等字段。

Save 不应保存纯 UI 状态，例如面板位置、展开折叠、临时 hover、镜头抖动、特效播放进度、纯视觉粒子状态。

若某些 UI 偏好需要保存，应作为用户设置或 UI 偏好保存，不得混入权威存档 State。

### 8. StateHash

StateHash 只覆盖影响玩法结果的权威状态。

StateHash 应覆盖：

- 资源；
- 建筑实例；
- 施工；
- NPC / 劳动力；
- 时间；
- 生产；
- 影响确定性结果的规则状态；
- 联机同步需要校验的一致性字段。

StateHash 不覆盖：

- UI 面板位置；
- 鼠标 hover；
- 摄像机临时位置；
- 粒子播放进度；
- 纯表现动画；
- 音效状态；
- 不影响玩法结果的本地偏好。

本轮不修改 StateHash 算法，只定义后续正式回写的覆盖边界。

### 9. ServerAuthority

ServerAuthority 是未来联机模式下的最终权威。

联机模式中：

- Server 执行权威 Simulation；
- Server 持有权威 State；
- Server 校验 Command；
- Server 输出权威 Event / Snapshot / StateHash；
- Remote Client 只提交 Command、预测表现或显示服务器结果；
- Remote Client 不推进权威 Simulation；
- Remote Client 不直接写权威 State。

单机模式和服务器模式应尽量共用 Simulation / RuntimeComposition，避免两套规则。

禁止创建第二套服务器专用资源库存、建筑系统、事件系统或总管理器。

## 三、RuntimeComposition 统一入口

RuntimeComposition 应作为 Runtime 系统组合入口，而不是新的总管理器平行体系。

RuntimeComposition 的职责是装配与连接：

- Definition 输入；
- State；
- Command 入口；
- Simulation 系统；
- Event 输出；
- Save / Load；
- StateHash；
- ServerAuthority 适配边界。

RuntimeComposition 不应复制资源库存、不应复制建筑状态、不应复制事件系统、不应另建和现有 Simulation 并行的总管理器。

正式回写时应明确：

```md
Simulation / RuntimeComposition 是单机与服务器共用权威入口。
UI / View 只能读取 Runtime 结果，不能修改权威 State。
所有玩家操作必须通过 Command。
Event 是事实输出，不是修改入口。
Save 只保存权威 State，不保存纯 UI 状态。
StateHash 只覆盖影响玩法结果的权威状态。
Remote Client 不推进权威 Simulation。
Server 才是联机权威。
不得创建第二套 Runtime 入口、资源库存、事件系统或总管理器。
```

应避免。

应避免。
